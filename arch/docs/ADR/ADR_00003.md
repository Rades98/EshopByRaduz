# ADR_00003: Monorepo per doména a sdílené vrstvy aplikace

**Status:** Proposed / Accepted  
**Date:** 2025-12-28  

---

## Context

Architektura e-shopu je založena na **DDD s více core doménami** (např. Checkout, Order, Stock, Pricing).  

Každá doména:
    - vystavuje více typů rozhraní (REST, gRPC, eventy),
    - má vlastní business logiku,
    - musí být nasaditelná a verzovatelná nezávisle na ostatních doménách.

Současně je požadováno:

- minimalizovat duplikaci kódu,
- zachovat konzistenci architektury napříč doménami,
- umožnit snadný vývoj a refactoring,
- udržet jasné hranice mezi doménovou logikou a technickou infrastrukturou.

---

## Decision

### 1. Každá doména má vlastní **monorepo**

Každá core doména je implementována v samostatném repozitáři:

- `catalog/`
- `pricing/`
- `stock/`
- `orders/`
- `checkout/`

Repozitář obsahuje **veškerý kód dané domény**, včetně API, workerů a infrastruktury.

---

### 2. Sdílená struktura vrstev v každém monorepu

Každý repozitář má jednotnou strukturu:

/domain
/application
/infrastructure

---

### 3. Sdílené vrstvy pro všechny typy rozhraní

V rámci jedné domény **neexistují oddělené domény pro API / worker / gRPC**.

Místo toho:

| Vrstva | Účel |
|------|------|
| Domain | Business logika, agregáty, pravidla |
| Application | Use-cases, orchestrace, transakce |
| Infrastructure | Technická implementace (API, DB, messaging) |

---

### 4. Typy vstupních bodů používají stejné vrstvy

| Typ rozhraní | Použití vrstev |
|--------------|----------------|
| REST API (WEB) | Application → Domain |
| REST API (ERP) | Application → Domain |
| gRPC | Application → Domain |
| Worker / Consumer | Application → Domain |

Rozdíl je **pouze ve vstupní vrstvě**, nikoliv v logice.

---

### 5. Infrastructure layer obsahuje

- REST controllery
- gRPC services
- Event consumers / producers
- Repository implementace
- Outbox / Inbox
- Integrace na externí systémy

Infrastructure:
- **závisí na Application**
- **nikdy na Domain opačně**

---

## Consequences

### Pozitiva
- Jednotná architektura napříč doménami
- Sdílená business logika pro všechny typy rozhraní
- Žádná duplicita use-cases
- Snadné testování
- Připravenost na microservices i modulární monolit
- Jasná struktura repozitáře

### Negativa
- Vyšší nároky na disciplínu vývojářů
- Nutnost hlídat hranice vrstev
- Větší počáteční návrhová práce

---

## Rationale

| Rozhodnutí | Důvod |
|-----------|------|
| Monorepo per doména | Jasné vlastnictví a izolace |
| Sdílené vrstvy | Eliminace duplicit |
| Jedna doména = jeden model | Konzistence dat i chování |
| Oddělená infrastruktura | Snadná výměna technologií |
| Více vstupních bodů | Podpora různých typů klientů |
